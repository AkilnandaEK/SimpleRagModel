- Supply chain: `mcp_config.json:15-19` runs `"npx", "-y", "package-registry-mcp"` with no version pin, so every host start downloads and executes whatever the `latest` dist-tag resolves to (2.1.0 today) and `-y` auto-confirms the install; even a pinned top-level dep would still float, because the bundle depends on `@modelcontextprotocol/sdk ^1.23.0` and `zod ^3.25.0` with no lockfile, and the pin cannot be verified over the protocol — `initialize` hardcodes `serverInfo.version "1.0.0"` in `dist/index.js:27575` even at 2.1.0, so the handshake reports a version that is not the code that is running.
- Local process execution and permissions: the server is spawned by `npx` as a child of the app and inherits the interactive user's full NTFS token — read/write access to the repo, `chroma_db/`, `traces/` and `.env` — with no sandbox, no command allowlist and no reduced-privilege account, so any code the registry serves runs unconfined; the server bundle itself is clean (0 matches for `child_process`, `execSync`, `spawn(`, `writeFile`, `eval(`), but the `npx` bootstrap step, not the server, is what fetches and executes third-party code.
- Environment variables and credentials: the MCP SDK's `get_default_environment()` allowlist (`APPDATA`, `USERPROFILE`, `LOCALAPPDATA`, `PATH`, `TEMP`, …) means `GEMINI_API_KEY` and `GROQ_API_KEY` are **not** passed to this third-party process — verified against the installed SDK, zero leaks — but the inherited `USERPROFILE`/`APPDATA` are precisely the variables that locate `~/.npmrc` and `%APPDATA%\npm\etc\npmrc`, so a registry `_authToken` stored there would be readable by the process (no such token exists on this host today); the bundle reads `process.env` 0 times and needs none of it.
- Network access and untrusted responses: the bundle hardcodes 7 outbound hosts (`registry.npmjs.org`, `api.nuget.org`, `azuresearch-usnc.nuget.org`, `crates.io`, `proxy.golang.org`, `pypi.org`, `api.github.com`) and returns their JSON verbatim as MCP `content[].text`, so attacker-controllable package metadata, descriptions and README text enters the model context directly (indirect prompt-injection surface); the server also signals upstream HTTP failure as *success* — a live `get-cargo-package-details` call returned `isError=false` with body `Error fetching package details: The request failed with status 403: Forbidden.` — so `isError` alone cannot be trusted to detect failure.
- Practical mitigations: pin the exact version (`"npx", "-y", "package-registry-mcp@2.1.0"`) and verify the tarball against a recorded `dist.integrity` hash, since the reported `serverInfo.version` is not trustworthy; declare an explicit minimal `env` block on the server entry in `mcp_config.json` so the SDK allowlist is not the only control; run it under a dedicated low-privilege account or container with no access to `.env`, `chroma_db/` or `traces/`; keep the agent's prompt-injection filter applied to all MCP observations; and treat every registry result as untrusted data rather than instructions, validating both `isError` and the response body before use.
